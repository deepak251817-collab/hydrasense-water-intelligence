# HydraSense ML Data Preparation Pipeline (Phase 5A)

This directory contains the Machine Learning data preparation pipeline for the **HydraSense Water Intelligence** platform.

## Overview & Scientific Disclaimer

> [!IMPORTANT]
> **Simulator Telemetry vs. Ground Truth**:
> 1. Telemetry generated by the sensor simulator is intended for system architecture development, pipeline verification, and integration testing.
> 2. Simulator scenario names are **NOT** treated as scientifically valid water-quality ground truth labels.
> 3. Real-world machine learning evaluation will integrate validated external public/research datasets placed in `ml/data/external/`.
> 4. Phase 5A builds the dataset preparation foundation. ML models (Isolation Forest, Random Forest, XGBoost, SHAP) will be introduced in subsequent phases.

## Feature Parameters

The ML pipeline strictly processes the four core water quality parameters and mandatory metadata:

- **Parameters**: `ph`, `turbidity`, `tds`, `temperature`
- **Metadata**: `station_code`, `device_id`, `timestamp`

---

## Data Cleaning & Range Validation Rules

### INVALID vs. UNUSUAL Data Policy

- **INVALID Data** (Removed during cleaning):
  - Values exceeding physical hardware or chemical physical limits:
    - **pH**: Outside `[0.0, 14.0]`
    - **Turbidity**: `< 0.0`
    - **TDS**: `< 0.0`
    - **Temperature**: Outside `[-10.0°C, 60.0°C]`
  - Non-numeric / missing mandatory metadata fields.

- **UNUSUAL Data** (Preserved during cleaning):
  - Statistical outliers that remain physically plausible (e.g. sudden drop of pH to 4.5, or spike of turbidity to 85 NTU) are **KEPT** in `clean_sensor_readings.csv`.
  - These unusual events represent real environmental spikes or contamination events required by anomaly detection algorithms (Isolation Forest) in later phases.

---

## Data Leakage Protection & Chronological Splitting

1. **Temporal Causality**:
   - Change features (`ph_change`, `turbidity_change`, `tds_change`, `temperature_change`) are calculated within each station ordered strictly by timestamp.
   - For row $t$, change is computed as $\text{val}_t - \text{val}_{t-1}$.
   - The initial observation per station sets change features to `0.0`, ensuring no future lookahead.

2. **Chronological Splitting**:
   - Time-series data is **NEVER randomly shuffled**.
   - Data for each station is partitioned chronologically into:
     - **70% Train** (Earliest timestamps)
     - **15% Validation** (Middle timestamps)
     - **15% Test** (Latest timestamps)
   - Order requirement: $\max(\text{train.timestamp}) \le \min(\text{val.timestamp}) \le \max(\text{val.timestamp}) \le \min(\text{test.timestamp})$.

## Running the Pipeline

### 1. Export Raw Sensor Data
```bash
python ml/scripts/export_sensor_data.py
```
Outputs `ml/data/raw/sensor_readings.csv`.

### 2. Generate Data Quality Report
```bash
python ml/scripts/data_quality_report.py
```
Displays terminal summary report of record counts, missing values, invalid values, and summary stats.

### 3. Clean Sensor Data
```bash
python ml/preprocessing/clean_data.py
```
Outputs `ml/data/processed/clean_sensor_readings.csv`.

### 4. Create Chronological Splits
```bash
python ml/scripts/create_splits.py
```
Outputs `train.csv`, `validation.csv`, and `test.csv` in `ml/data/processed/`.
